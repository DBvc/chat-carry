# 以后新增一个 AI 平台

这是后续接入约定，不是 v0.1 的实现待办。当前生产 registry 只有 ChatGPT。

## 平台边界统一什么

统一：识别当前 origin、读取并归一化当前会话、交付前复核、Conversation 模型、两种输出、错误体验。
不统一：内部接口、鉴权流程、页面结构、分支算法、Markdown 来源、引用元数据或完整性证明方式。
不同平台可以用不同采集策略；不能要求全体平台模拟 ChatGPT 的 mapping/current_node。

## 最小接入流程

1. 明确该平台的精确 origin、路由、支持的账户与会话范围；公开文档/当前真实页面核实数据来源，不能猜端点或要求用户提供凭证。
2. 新建 providers/<id>/，实现同一 ChatAdapter。简单平台一个 index.ts 即可，只有出现实际复杂逻辑才拆 capture/normalize；不照抄 ChatGPT 文件数量。
3. read 返回归一化的 Conversation 与 assertCurrent。来源、当前分支、生成状态、未知内容和缺失正文分别处理；不给不确定的 DOM 片段盖上 complete。
4. 用独立脱敏 fixture 验证读取、归一化、消息顺序、格式、引用占位与拒绝路径；通用 renderer 测试继续复用。
5. 精确域名匹配并检查权限。在 activeTab 的用户主动读取范围内尽量复用原权限；确有跨 origin/新能力需求时单独说明并审查最小授权，不一律增加全站读取。
6. 实际实现并通过测试后，在 providers/index.ts 显式 import 并注册。README 分别写“已支持”“测试版”“计划”，不能把目录存在当成已支持。
7. 运行原有 ChatGPT 回归、所有通用契约、该平台浏览器和授权真实会话测试。失败不能污染另一个平台。

## 通过标准

交付前能确认同一 tab、来源、当前对话与所选路径；文本保真、代码缩进、中文和 Emoji 正确；
不导出未呈现给用户的隐藏指令/推理；不静默丢正文；不泄漏原始凭证；两个按钮仍是默认 UI。

有些平台可能拿不到可靠全量数据。可以先不发布这个 adapter，或以后另立明确“片段导出”产品范围，
但本期不能把 partial / unknown 自动转为 complete，也不能偷偷增加高级设置来躲过验收。

## 有意不预建

没有 BaseProvider、万能 HTTP 客户端、全平台 selector DSL、ProviderCapabilities 矩阵、
动态插件 SDK、后台收集、跨 AI 导入/续聊、自动同步。相同实现真的重复且变化方向一致时，再抽小函数。
当前快照以 body + format 为正文契约，未来真实格式保真需求超出它时再演进，不承诺该接口永远不改。
